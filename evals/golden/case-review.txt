ISSUE #6756
TITLE: [bug]: cURL import decodes literal --data-urlencode content
STATE: OPEN
CREATED: 2026-10-29T01:34:16Z
LABELS:
BODY:
### Is there an existing issue for this?

I searched existing issues and PRs for `data-urlencode`, `dataUrlencode`, cURL decoding, percent characters and URIError. Related reports are discussed below; I did not find the same literal-content case.

### Platform / environment

Local source checkout on Windows, commit `63273f8e599e73f0fb38c0739314e8d46b6bc83d`. Reproduced through the existing Web App cURL parser unit-test path, not a browser session or a deployed release. No interceptor is involved in this import-time failure.

### Bug Description

`--data-urlencode name=content` takes literal content and asks curl to encode it. The importer instead decodes the complete argument before parsing its key/value pair, then decodes the pair again.

For example:

```sh
curl 'https://example.com/api' --data-urlencode 'query=100% free'
```

Calling `parseCurlToHoppRESTReq` with this command throws `URIError: URI malformed` at the initial `A.map(decodeURIComponent)` in `curlparser.ts`. Other valid inputs import silently with different values:

| Literal argument | Imported value | Expected value |
| --- | --- | --- |
| `query=100%25` | `100%` | `100%25` |
| `query=a%20b` | `a b` | `a%20b` |

The same literal-content rules apply when `-G` sends the fields as query parameters.

### Evidence

The [official curl manual](https://curl.se/docs/manpage.html#--data-urlencode) specifies that `name=content` encodes the content while the name is already URL encoded. A local HTTP echo server with real curl 8.21.0 confirms:

```text
input: query=100%25
wire:  query=100%2525
decoded by the receiving server: query = 100%25
```

Twenty local curl requests verified POST / `-G`, literal percent signs, encoded-looking values, plus signs, spaces, equals signs, Unicode, repeated flags and pre-encoded field names. The new parser cases fail against the base implementation (9 failures, 40 passes); a local fix passes the complete cURL helper suite (62 tests across 2 files).

### Proposed fix for discussion

Keep `--data-urlencode` content literal, split at the first `=`, and decode only the already encoded name once, including `+` as a space in the name. Keep the existing handling of ordinary `--data`, `--data-raw`, and URL query parameters. A small tested patch is prepared for review; feedback on the importer contract is welcome.

This proposal covers inline `name=content` only. It does not add file/stdin loading, the other `--data-urlencode` input forms, mixed data flags or new handling of `--get` option placement.

### Related work

- #3901 / #3905 addressed missing JSON-valued fields in `--data-urlencode` imports; the old issue is closed and PR merged.
- #5645 proposed broad safe decoding / preprocessing for complex JSON/XML imports and was closed without merging. Its diff does not change the initial `dataUrlencode` decoding.
- #6353 changes URL sanitization and shell preprocessing, with different regression cases; its diff does not modify this `dataUrlencode` conversion.


AI assistance: Codex assisted with investigation, implementation and the executed tests.

ISSUE #6750
TITLE: Collection runner stays running after Stop during a request delay
STATE: OPEN
CREATED: 2026-10-27T02:09:16Z
LABELS:
BODY:
### Bug description

Stopping a collection run while it is waiting between requests leaves the runner in the `running` state until the entire configured delay has elapsed. With a 60-second delay, stopping just after a request completes can take nearly a minute. No subsequent request should start after Stop is pressed.

### Steps to reproduce

1. Create a collection with two quick requests and open the collection runner.
2. Set the delay to 60,000 ms and start the run.
3. After the first request finishes and before the second starts, press Stop.
4. Observe that the runner remains running until the delay completes.

### Expected behavior

The runner should stop promptly while waiting and should not execute the next request.

### Investigation

On `main` at `63273f8`, the runner awaits a plain `setTimeout` after each request. Its stop ref is checked before starting a request, but it is not observed while waiting. A local regression test against the real `TestRunnerService` fails before a candidate fix and passes with a stop-aware delay. An ordinary run still observes its configured delay.

Would the maintainers welcome a focused fix that cancels the outstanding delay when the stop ref changes? The candidate has been tested with two relevant Vitest files (19 tests passed) and changed-file ESLint. Browser acceptance has not yet been run. AI assistance was used for the investigation and candidate change.

STATE: OPEN
CREATED: 2026-10-26T13:39:30Z
LABELS:
BODY:
### Problem

Adding another subscription root field in the schema explorer appends an operation with the selected operation's name. The resulting document has duplicate operation names and cannot execute. Both unified and standalone GraphQL builders are affected on `main` at `63273f8e599e73f0fb38c0739314e8d46b6bc83d`.

### Reproduction

Use `type Query { read: String } type Subscription { first: String second: String }` and this valid document:

```graphql
subscription First { first }
```

Place the cursor in `First`, open the Subscription root in the schema explorer and add `second`. The builder appends:

```graphql
subscription First { second }
```

GraphQL validation reports `There can be only one operation named "First".` The selected operation's in-memory AST is also changed to the new field.

Expected: retain the original subscription and append an independent subscription with one root field and a name unused in the document. Names used by query/mutation operations must also be respected. Adding/removing the same field should retain its existing behavior.

### Verification

Reproduced through the production service and standalone composable, real explorer state and GraphQL parse/validate on Windows, Node 22.23.4 and pnpm 10.34.5. Four regressions fail against the original implementations, with ordinary query/mutation and same-field controls passing. No deployed-browser or provider request is claimed.

Investigated with OpenAI Codex; no real credentials, external APIs or user data are involved.
